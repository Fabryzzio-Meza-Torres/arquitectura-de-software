# 7. Key product decisions

1. **Human authority.** The LLM only proposes. Support or engineering reviews, performs the solution, and records the outcome. An Approval Gate blocks destructive recommendations; no LLM-connected tool has production write permission.
2. **Types and deadlines.** A client-origin ticket keeps its one-day deadline when it moves from support to engineering. A ticket created by engineering has a three-day deadline. Priority considers urgency and remaining time; equal-priority tickets use arrival order.
3. **Escalation.** If information is missing, the system requests it. If the LLM fails, has insufficient evidence, exhausts limits, or a person rejects the proposal, the ticket stays visible and can be escalated. Jesus assigns Julia or another person; the Harness never assigns the solution itself.
4. **Knowledge.** Only human-validated resolved tickets feed the RAG index during the nightly update. Answers include source and freshness; a proposal without evidence is identified as such.
5. **Consistency.** Idempotency applies per operation and ticket, notifications are deduplicated, common-question cache entries are versioned, and live ticket status is read from the current record. Closing or reopening invalidates related entries. Retries do not duplicate actions.
6. **Resilience.** Request and token limits, a persistent priority queue, load balancing, timeout, bounded retries, circuit breaker, fallback, and a dead-letter queue preserve work during peaks or failures. Repeated failures go to human review.
7. **Integration boundaries.** Database MCP access is authorized and minimal read-only access; the sandbox runs isolated tests without production data; Slack MCP delivers escalation notifications. Subagents and loop control operate under the same Harness permissions and limits.
